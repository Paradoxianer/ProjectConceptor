151// bigtime_t is microseconds - this was 10 (i.e. 0.01ms), which meant
152// LockWithTimeout() calls sharing this constant (PCommandManager::Execute(),
153// GraphEditor::ValueChanged(), PDocumentManager) failed under almost any
154// real lock contention rather than the rare/exceptional case a timeout is
155// meant to guard against. Confirmed as the direct cause of a live crash:
156// GraphEditor::ValueChanged() proceeded to iterate PDocument's changedNodes
157// set without actually holding the lock whenever this timeout fired,
158// racing against PCommandManager::Execute() clearing/repopulating that
159// same set on another thread (see the fix at GraphEditor.cpp's
160// ValueChanged()). 50ms comfortably covers normal command execution time
161// without making a genuinely stuck lock hang the UI for long.
162const bigtime_t TIMEOUT_LOCK = 50000;
